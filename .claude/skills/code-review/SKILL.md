# コードレビュー

プロジェクト規約と一般的なコード品質基準に基づいてコードをレビューするスキル。

## ワークフロー

### 1. レビュー対象の特定

```
ユーザーリクエスト
    ├── "変更をレビューして" → git diffを取得
    ├── "PRをレビューして" → PR全体のdiffを取得
    ├── "このファイルをレビューして" → 指定ファイルを読み込み
    └── 具体的な指定なし → git statusで変更を確認
```

### 2. コンテキスト収集

レビュー前に以下を確認:
- プロジェクト規約: `CLAUDE.md` と `.claude/rules/*.md`
- 関連ファイル: 変更が影響する既存コード

### 3. レビュー実行

観点ごとにコードを分析し、問題点と改善提案を出力。

## レビュー観点

### プロジェクト規約チェック

`.claude/rules/` の規約への準拠を確認。詳細は [references/project-rules.md](references/project-rules.md) を参照。

主なチェックポイント:
- 言語設定（コメント・エラーメッセージは日本語）
- インポートパス（`@/` エイリアス使用）
- TypeScript strict mode準拠
- コンポーネント配置（ui/, budget/, auth/, pages/）
- データフロー（Service層 → Hooks → Components）
- エラーハンドリングパターン
- テスト配置と命名

### 一般的なコード品質

詳細は [references/code-quality.md](references/code-quality.md) を参照。

主なチェックポイント:
- 可読性: 命名、構造、複雑度
- 保守性: 単一責任、DRY、適切な抽象化
- パフォーマンス: 不要な再レンダリング、メモ化、クエリ最適化
- セキュリティ: XSS、インジェクション、認証・認可

## 出力フォーマット

```markdown
## レビュー結果

### 概要
[変更の要約と全体的な評価]

### 問題点

#### 重大 (修正必須)
- [ファイル:行] 問題の説明
  - 理由: なぜ問題か
  - 提案: 修正方法

#### 警告 (改善推奨)
- [ファイル:行] 問題の説明
  - 提案: 改善方法

#### 提案 (検討事項)
- [ファイル:行] 提案内容

### 良い点
- [ポジティブなフィードバック]
```

## コマンド例

```bash
# ステージングされた変更をレビュー
git diff --cached

# 特定ブランチとの差分をレビュー
git diff main...HEAD

# PRの変更を取得
gh pr diff <PR番号>
```
